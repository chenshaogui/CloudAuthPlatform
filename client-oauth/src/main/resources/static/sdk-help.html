i项目概述

cloud-auth-client-oauth 是统一授权认证中心的客户端 SDK，以插件方式集成到业务系统。

它负责：

  • 与认证中心完成 SSO 单点登录（基于 sa-token-sso）；
  • 从认证中心统一拉取用户、菜单路由、机构、权限码、字典、参数配置等数据；
  • 提供 @SaCheckPermission / @SaCheckRole 等注解的本地 O(1) 校验；
  • 自动跟随认证中心的权限变更（节流式后台同步）。
SDK 已内置 CloudTokenSsoClientController(/sso)、CloudAuthCenterController(/authCenter)、CloudOssController(/authCenter/oss) 三组端点，业务方无需手写；如需自定义返回结构（如包装为项目内的 R<T>）或扩展 Swagger 注解，在自身工程定义同名 Controller 即可（Spring 优先加载业务方 Bean）。

1Maven 依赖

本 SDK 的 artifactId 统一用占位符 ${cloud-auth-client-oauth.version} 表示（当前值为 1.5.11，与 pom.xml 中 io.gitee.chenshaogui.cloudauth:cloud-auth-client-oauth 版本一致）。

SpringBoot 2.x 项目

<dependency>
  <groupId>io.gitee.chenshaogui.cloudauth</groupId>
  <artifactId>cloud-auth-client-oauth</artifactId>
  <version>${cloud-auth-client-oauth.version}</version>
</dependency>
<dependency>
  <groupId>cn.dev33</groupId>
  <artifactId>sa-token-spring-boot-starter</artifactId>
  <version>1.44.0</version>
</dependency>

SpringBoot 3.x 项目（jakarta.servlet）

<dependency>
  <groupId>io.gitee.chenshaogui.cloudauth</groupId>
  <artifactId>cloud-auth-client-oauth</artifactId>
  <version>${cloud-auth-client-oauth.version}</version>

2application.yml 配置

全部配置都挂在 sa-token 命名空间下（与 sa-token 官方共享前缀）。一部分由 sa-token 官方 SaTokenConfig / SaSsoClientConfig 解析，一部分由本 SDK 的 CloudProperties、环境后处理器、CORS 与缓存模块解析。下表按「归属分组」逐一列出 SDK 会读取的全部配置项。

上述各配置项在不同接入方式下的完整 application.yml 模板，见下方「方式一：仅单点登录 / 方式二：完全接入（推荐）」章节。

3方式一：仅单点登录（老项目保留自有用户体系）

老项目已有自己的用户 / 角色 / 权限体系，只借用统一认证平台的「统一登录」能力；登录后用户信息、菜单、权限仍由业务系统自身管理。

关键配置：sa-token.only-login: true（其余按 sa-token 官方 SSO 客户端配置即可）。

方式一推荐使用 getUserInfoByTicketWithoutLogin(ticket) 拉取用户信息（不消费 ticket、不自动登录）；误用 getUserInfoByTicket(ticket) 会消费 ticket 并自动完成本地登录。

application.yml 配置示例

sa-token:
  token-name: Authorization
  only-login: true                     # 仅做单点登录（方式一必填）
  sso-client:
    client: b3ed3d93b017ba5921e014efc78a6ad6
    server-url: https://example.com/uaa-gateway/auth
    auth-url: https://example.com/etc2-html/cloudAuthPlatform/index.html#/ssologin
    is-http: true
    secret-key: REPLACE_WITH_SECRET_KEY

4方式二：完全接入（推荐）

客户端所有用户、角色、菜单、权限码均由认证中心统一管理，业务系统只做渲染与业务处理。推荐新项目或直接重构接入的项目使用。

关键配置：不配置 only-login 或显式 only-login: false，并完整配置 sso-client 及 sa-token 相关项。

application.yml 配置示例

sa-token:
  token-name: Authorization            # token / cookie 名称
  check-same-token: true               # 开启内网服务调用鉴权
  is-log: true                         # 打印操作日志
  sso-client:
    client: sso-client3                # 应用标识（必填，由认证中心分配）
    server-url: http://sa-sso-server.com:9000  # 认证中心地址
    is-http: true                      # 使用 HTTP 校验 ticket
    secret-key: REPLACE_WITH_SECRET_KEY  # API 调用秘钥
  # 微服务多模块时，仅登录入口模块（如 system）开启 Controller，其余关闭：
  expose-controller: true

9前端对接方式（ticket 防重复消费）

面向接入统一认证平台的各子系统前端。统一认证平台的 ticket 为一次性票据，同一张 ticket 只能消费一次；中转页需保证每个 ticket 只提交一次。配套阅读：认证中心接入指南（中转页创建、路由白名单、退出登录）。

背景与现象

以 silent 静默授权为例链路：中转页拿登录地址 → 认证中心已登录自动回跳并签发一次性 ticket（...?back=业务页&ticket=64位）→ 中转页调 GET /sso/doLoginByTicket?ticket=xxx → 认证中心校验后立即删票返回本地 token。

ticket 是明文 query 参数，会残留在地址栏与历史记录。back 为空、F5 刷新、浏览器后退、请求双发都会用同一张票再次请求，此时票据已失效返回「无效 ticket」。若前端把该错误统一按「登录超时 / 401」处理而 removeToken()，就会再次跳认证中心 → silent 又免登回来，表现为登录态反复消失、闪屏、循环重新登录。

前端必须落实的 4 点

序号动作解决的问题
①消费后立即清洗 URL：history.replaceState(null,'',location.pathname+location.hash)，成功 / 失败两条路径、跳转前都要执行刷新、后退时地址栏不再有 ticket
②跳 back 用 location.replace(back || '/')，back 为空兜底业务首页；不要用 location.href / router.push避免停留在带票页面，且历史不留回跳页
③已登录短路：进入中转页先探测本地登录态，已登录直接跳 back，不再消费 ticket刷新 / 后退 / 多标签进入时天然幂等
④错误分类：把「无效 ticket / 票已消费」与「登录超时」区分开；本地 token 仍有效时按已登录处理，不 removeToken()、不立即重新发起 silent 授权直接消除「登录消失」
③ 的重要前提：本地登录态探测可用 GET /authCenter/getLoginUserInfo，未登录会返回 401，该探测请求必须排除在全局 401 拦截器之外，否则探测本身就会清掉有效 token。④ 配套：request.ts / permission.ts 中「401 → 清 token → 跳 /sso」要加限定，仅本地 token 确实失效才触发重新授权。

参考实现（Vue3 中转页 onMounted）

const ticket = getParam('ticket');
const back = getParam('back') || '/';
const cleanUrl = () => history.replaceState(null, '', location.pathname + location.hash);

// ③ 轻量探测：请求需跳过全局 401 拦截（skipAuthRedirect 等标记）
const isLocalLoginValid = async () => {
  try {
    await request({ url: '/authCenter/getLoginUserInfo', skipAuthRedirect: true });
    return !!getToken();
  } catch { return false; }
};

// ④ 只把「票据已消费」类错误归为可忽略
const isTicketInvalid = (e) =>
  /无效\s*ticket|ticket.*(已消费|失效|无效)|30004/i.test(e?.msg || e?.message || '');

onMounted(async () => {
  if (!ticket) { goSsoAuthUrl(); return; }

  // ③ 已登录短路：刷新 / 后退 / 多标签进入时不再消费票据
  if (await isLocalLoginValid()) { cleanUrl(); location.replace(back); return; }

  // 防重：同一张票在并发或重复挂载下只提交一次
  const key = 'sso_ticket_' + ticket;
  if (sessionStorage.getItem(key)) { cleanUrl(); location.replace(back); return; }
  sessionStorage.setItem(key, '1');

  try {
    const res = await userStore.ticketLogin({ ticket });   // POST /sso/doLoginByTicket
    localStorage.setItem('satoken', res.data.accessToken);
  } catch (e) {
    // 票已消费但本地 token 有效 → 按已登录继续，不清理登录态
    if (!isTicketInvalid(e) || !(await isLocalLoginValid())) {
      sessionStorage.removeItem(key); cleanUrl(); goSsoAuthUrl(); return;
    }
  }

  // ①② 先清洗地址，再 replace 到业务页（back 为空时进首页）
  cleanUrl(); location.replace(back);
});

goSsoAuthUrl() 保持原有逻辑：/sso/getSsoAuthUrl 或 /sso/getEncryptedSsoAuthUrlForSilent，clientLoginUrl 传中转页地址，back 传用户原本要去的业务页。

验收清单

场景期望结果
首次 silent 授权回跳登录成功，地址栏无 ticket，直接进业务页
登录成功后 F5 刷新不再请求 /sso/doLoginByTicket，或由已登录短路直接跳回；登录态保持
浏览器后退到回跳地址不带票 / 短路跳过，不出现「无效 ticket」与重新登录
back 为空或为 undefined进入业务首页，不停留在带票页面
主动登出后再访问清本地 token 与 sessionStorage 防重标记，重新走 SSO 能正常登录
多实例部署 / 服务重启行为一致（与后端节点无关）

参考数据sa-token.cache.reference-ttl-seconds300 秒部门 / 字典 / 参数配置 / 区域 / 公告 / 文件类接口
用户信息sa-token.cache.user-ttl-seconds60 秒getUserInfoById / getUserListByIds
单接口例外优先级最高：sa-token.cache.{apiName}.ttl-seconds（如 getDictDataByType.ttl-seconds: 600）。未集成 Redis 时自动降级为「不缓存、每次远程调用」。

11白名单与 CORS

登录白名单

SDK 硬默认白名单 ["/sso/*", "/favicon.ico"] 永远生效（登录前即可访问）。/sdk-help.html 不在默认白名单中，其是否对外暴露由客户端系统自行决定；需要访问时，用 sa-token.permit-paths 追加：

sa-token:
  permit-paths:
    - /admin-api/system/sms/callback/**
    - /admin-api/openapi/webhook/**
    - /admin-api/public/health

CORS 配置

sa-token:
  client:
    cors:
      allowed-origins: https://app.example.com   # 默认 *
      allowed-methods: GET,POST,PUT,DELETE,OPTIONS
      allowed-headers: Authorization,Content-Type,X-Requested-With
      max-age: 3600
网关若带 /admin-api 前缀，需做 RewritePath 剥掉前缀（SDK 控制器映射不带业务前缀），否则白名单放行后仍 404。详见接入实践文档。
