# 认证中心服务端改造 — 注册自动绑定角色

> 配套 SDK 版本：**cloud-auth-client-oauth 1.4.0**（SDK 侧改动已完成，见文末）
> 服务端工程：`D:\project\cloud-auth-platform`
> 需求：用户注册后没有任何角色 → PC 端看不到菜单，还需管理员手工配置。
> 目标：客户端 SDK 可配置角色标识（`sys_role.role_key`，可多个），注册完成后服务端**自动绑定**这些角色；配置无值则行为完全不变；**仅当用户尚未绑定任何角色时才绑定**（不覆盖已有配置）。

---

## 一、方案总览（数据流转链路）

```
客户端 SDK 配置 sa-token.register-role-keys
        │  (SDK wrapRegisterBody 注入到注册 body JSON)
        ▼
POST /sso/pushS  type=register   body={"username":...,"roleKeys":["common_user"],...}
        ▼
SsoServerController register handler → 反序列化 RegisterBody          【改①：加 roleKeys 字段】
        ▼
SysLoginService.register → RemoteUserBo                              【改②：透传 roleKeys】
        ▼  (Dubbo)
RemoteUserServiceImpl.registerUserInfo → SysUserBo                   【改③④：加字段+显式透传】
        ▼
SysUserServiceImpl.registerUser → autoBindRolesByRoleKeys            【改⑤：核心绑定逻辑】
        ▼
sys_user_role 批量插入（用户无角色时才绑定，过滤超管，未命中静默跳过）
```

共 **6 个文件、12 处修改**。全部为增量修改，不影响现有注册、登录、管理员 addUser 等任何链路。

**3. 新增私有方法 `autoBindRolesByRoleKeys`**

插入位置：`insertUserRole(SysUserBo user, boolean clear)`（约第 546~554 行）的 javadoc **之前**，即：

```java
    /**
     * 注册后按角色标识（sys_role.role_key）自动绑定角色
     * <p>规则：
     * 1. roleKeys 为空直接返回（向后兼容，行为与改造前完全一致）；
     * 2. 仅当该用户在 sys_user_role 中尚无任何绑定时才执行（已配置过的不覆盖，天然幂等）；
     * 3. sys_role 为租户隔离表，按注册租户 TenantHelper.dynamic 切上下文查询；
     * 4. role_key 库内为完整格式 {clientId}-{权限标识}（新建角色时的统一规则），
     *    故对每个配置值做双格式兼容：原值 + clientId 补全值 一并精确匹配；
     * 5. 超级管理员角色禁止经注册通道自动绑定（防提权）；
     * 6. 未命中任何启用角色时静默跳过，只记 warn 日志，不影响注册结果；
     * 7. 与 registerUser 同事务，绑定失败则注册整体回滚。</p>
     *
     * @param userId   新注册的用户ID
     * @param roleKeys 角色标识列表（可空；支持短标识或完整 {clientId}-标识）
     * @param tenantId 注册租户ID
     * @param clientId 注册来源客户端ID（用于补全短标识）
     */
    private void autoBindRolesByRoleKeys(Long userId, List<String> roleKeys, String tenantId, String clientId) {
        if (CollUtil.isEmpty(roleKeys) || userId == null) {
            return;
        }
        TenantHelper.dynamic(tenantId, () -> {
            // 前提：用户没有绑定角色时才绑定（已有配置不覆盖）
            boolean bound = userRoleMapper.exists(
                new LambdaQueryWrapper<SysUserRole>().eq(SysUserRole::getUserId, userId));
            if (bound) {
                log.info("注册自动绑定角色跳过：用户已绑定角色, userId={}", userId);
                return;
            }
            // 双格式兼容：库里 role_key 是 {clientId}-{权限标识}，配置短标识时自动补全后一起精确匹配
            List<String> candidates = new ArrayList<>(roleKeys.size() * 2);
            for (String key : roleKeys) {
                if (StringUtils.isBlank(key)) {
                    continue;
                }
                String k = key.trim();
                if (!candidates.contains(k)) {
                    candidates.add(k);
                }
                if (StringUtils.isNotBlank(clientId)) {
                    String full = clientId + "-" + k;
                    if (!candidates.contains(full)) {
                        candidates.add(full);
                    }
                }
            }
            if (candidates.isEmpty()) {
                return;
            }
            // 按 role_key 命中启用状态的角色（MP 逻辑删除自动过滤 del_flag）
            List<SysRole> roles = roleMapper.selectList(
                new LambdaQueryWrapper<SysRole>()
                    .in(SysRole::getRoleKey, candidates)
                    .eq(SysRole::getStatus, SystemConstants.NORMAL));
            if (CollUtil.isEmpty(roles)) {
                log.warn("注册自动绑定角色：未命中任何启用角色, roleKeys={}, userId={}, 跳过绑定", roleKeys, userId);
                return;
            }
            List<SysUserRole> userRoles = new ArrayList<>(roles.size());
            for (SysRole role : roles) {
                // 防提权：超级管理员角色不允许通过注册通道自动绑定
                if (SystemConstants.SUPER_ADMIN_ID.equals(role.getRoleId())) {
                    log.warn("注册自动绑定角色：忽略超级管理员角色, roleId={}, userId={}", role.getRoleId(), userId);
                    continue;
                }
                SysUserRole ur = new SysUserRole();
                ur.setUserId(userId);
                ur.setRoleId(role.getRoleId());
                userRoles.add(ur);
            }
            if (CollUtil.isNotEmpty(userRoles)) {
                userRoleMapper.insertBatch(userRoles);
                log.info("注册自动绑定角色成功: userId={}, roleKeys={}", userId, roleKeys);
            }
        });
    }

    /**
     * 新增用户角色信息
     *
     * @param user  用户对象
     * @param clear 清除已存在的关联数据
     */
    private void insertUserRole(SysUserBo user, boolean clear) {
        this.insertUserRole(user.getUserId(), user.getRoleIds(), clear);
    }
```

> 注：新用户注册后尚未登录，本地/远端均无登录态缓存，无需发 `PermissionChangeEvent` 权限同步通知（与 `insertUser` 中“新用户尚未登录，无需权限同步通知”的既有语义一致）。

> 后续重构（`addUser` 用户已存在时补绑角色）：`autoBindRolesByRoleKeys` 的内部逻辑已抽取为
> `bindRoleKeys(userId, roleKeys, clientId, onlyWhenNoRoles)`。注册链路传 `true`（用户已有任何绑定即整体跳过，
> **行为完全不变**），`addUser` 补绑链路传 `false`（保留已有绑定，只追加缺失的 roleId，按 roleId 去重）。
> 日志前缀由“注册自动绑定角色”统一为“自动绑定角色”，双格式匹配、启用状态过滤、超级管理员过滤、
> 未命中静默跳过等规则均不变；补绑链路新增绑定后会发 `PermissionChangeEvent(UPDATE)` 刷新在线用户权限。

## 三、安全与边界规则（评审要点）

| 场景 | 行为 |
|---|---|
| SDK 未配置 `sa-token.register-role-keys`（无值） | 注册 body 不含 roleKeys → 服务端全链路 null-safe 直接跳过，**行为与改造前完全一致** |
| 用户已有角色（历史用户重复注册不可能；防并发/防手工干预） | `exists` 检查命中 → 跳过，不覆盖管理员已配置的角色 |
| role_key 配错 / 角色被禁用（status≠0）/ 已删除 | 查询不命中 → warn 日志，静默跳过，注册照常成功 |
| 配置填**短标识**（如 `admin`） | 服务端用注册消息里的 clientId 自动补全为 `{clientId}-admin` 再匹配（与新建角色入库规则一致，见下方 role_key 格式说明），只会命中本客户端的角色 |
| 配置填**完整标识**（如 `a0ba2cb22eb6f1006ed2f054-admin`） | 直接精确命中 |
| role_key 指向超级管理员角色 | 命中后按 `SUPER_ADMIN_ID` 过滤剔除，**防提权** |
| 业务方注册时显式传了 `CloudRegisterBo.roleKeys` | 优先使用显式值，客户端配置只做兜底（SDK 侧已实现） |
| 多次注册重试 | exists + 插入同事务，天然幂等 |

## 三点五、role_key 在授权中心的存储格式（务必先读）

服务端 `sys_role.role_key` 入库时统一拼了客户端前缀，**库里存的是完整串** `{clientId}-{权限标识}`：

- 管理台新建角色：`SysRoleController#add`（86~89 行）
  `role.setRoleKey(role.getClientId() + "-" + role.getRoleKey());`
- 客户端管理员角色：`SysClientAdminRoleBinder`（80 行）
  `role.setRoleKey(role.getClientId() + "-admin");`

因此本方案的匹配逻辑做了**双格式兼容**：配置里填 `admin` 或 `a0ba2cb22eb6f1006ed2f054-admin` 都能命中——
短标识由服务端用注册链路透传的 clientId（SDK 上报的自身客户端 ID）补全后再按 `role_key` 精确查询。

**推荐填短标识**（如 `admin`、`common_user`）：可读性好、且天然限定只命中本客户端的角色。
⚠️ 注意：填 `admin` 自动补全后命中的是 `{clientId}-admin` **客户端管理员角色**，即注册用户一进来就是该客户端管理员，请确认这是期望的权限；一般业务角色请配对应短标识。

## 五、验证清单

1. **不配置（回归）**：SDK 不配 `register-role-keys`，走图形码/短信码注册 → `sys_user_role` 无新记录，注册成功，行为不变。
2. **正常绑定（短标识）**：SDK 配置 `sa-token.register-role-keys: [admin]` 等短标识 → 服务端自动补全为 `{clientId}-admin` 命中，新注册用户 `sys_user_role` 出现对应记录；PC 端登录后菜单可见。
3. **正常绑定（完整标识）**：配置 `sa-token.register-role-keys: [a0ba2cb22eb6f1006ed2f054-admin]` → 直接精确命中，效果同上。
4. **前提校验**：手工给某用户已绑定角色后再模拟（或直接调注册）→ 日志出现“自动绑定角色跳过”，原绑定不变。
5. **防提权**：配置 `register-role-keys: [superadmin对应key]` → 不绑定，日志“忽略超级管理员角色”。
6. **无效 key**：配置一个不存在的 key → 注册成功，日志“未命中任何启用角色”。
