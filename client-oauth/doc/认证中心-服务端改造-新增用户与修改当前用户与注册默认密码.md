# 认证中心-服务端改造：新增用户 / 修改当前登录人信息 / 注册密码可选

> 目标工程：`D:\project\cloud-auth-platform`（认证中心服务端）
> 配套 SDK：`D:\project\cloud-auth-client-oauth`（本仓库，`cloud-auth-client-oauth`）
>
> 本文档描述**服务端**需要落地的改动。SDK 通过 sa-token **pushS 消息总线**调用认证中心，
> 每个能力对应一个 `message type` handler（注册在 `SsoServerController` 的
> `configSso` / `configAuth` 里）。服务端按本文补齐 handler 与 Dubbo 方法后，
> SDK 侧只需按“总线契约”发对应 type 即可，无需认证中心再改。

## 1. 现状梳理（改造前）

### 1.1 注册链路（需求3 相关）
```
SDK /sso/register
  → 总线 type="register"
  → SsoServerController.configAuth 的 "register" handler
  → TokenController.register(RegisterBody)   // @Validated 触发 RegisterBody 上的校验
  → SysLoginService.register(RegisterBody)   // 组装 RemoteUserBo，BCrypt.hashpw(password)
  → RemoteUserService.registerUserInfo(RemoteUserBo)
  → SysUserServiceImpl.registerUser(...)     // 落库 + 按 roleKeys 自动绑定角色
```

关键点：
- `RegisterBody.password` 当前带 `@NotBlank` + `@Length(min=5,max=30)`，**密码为空会被直接拒绝**。
- `SysLoginService.register` 第 222 行 `remoteUserBo.setPassword(BCrypt.hashpw(password))`
  **无条件加密**，即使前端不传密码也会被加密成“空串的哈希”，导致下游识别不出“未填密码”。
- `RemoteUserServiceImpl.registerUserInfo` **已经**实现了“密码为空 → 取默认密码 `sys.user.initPassword` 并加密”：
  ```java
  if (StringUtils.isBlank(sysUserBo.getPassword())) {
      TenantHelper.dynamic(remoteUserBo.getTenantId(), () -> {
          String initPassword = configService.selectConfigByKey("sys.user.initPassword");
          sysUserBo.setPassword(BCrypt.hashpw(initPassword));
      });
  }
  ```
  所以需求3 **只需打通上游两处**（放开校验 + 空密码不预置哈希），默认密码逻辑无需新增。

### 1.2 可复用的用户服务能力
- `RemoteUserService.registerUserInfo(RemoteUserBo)`：用户名/手机号唯一性校验、默认密码兜底、
  按 `roleKeys`（角色编码）自动绑定角色 —— 需求1 直接复用。
- `ISysUserService.updateUserProfile(SysUserBo)`：更新 `nickName / phonenumber / email / sex` —— 需求2 复用。
- `ISysUserService.checkPhoneUnique(SysUserBo)` / `checkEmailUnique(SysUserBo)`：唯一性校验（按 userId 排除自己）。

### 1.3 `RemoteUserBo` 关键字段（总线 body 反序列化目标）
`userId / tenantId / clientId / deptId / userName / nickName / email / phonenumber / sex / password / status / remark / roleKeys(List<String>) / userSourceType`

## 2. 总线契约（SDK ↔ 服务端对齐）

body 均为**单个 JSON 字符串**放在消息参数 `body` 里（SDK `CloudPlatformHelper.wrapBody` 已如此封装）；
`loginId`、`client` 由 SDK 随消息自动上报（登录态接口）。

### 2.1 `addUser`（需求1）
请求 body 字段：
```jsonc
{
  "userName": "zhangsan",       // 必填，登录账号
  "password": "abc@1234",       // 选填；为空 → 走默认密码 sys.user.initPassword
  "phonenumber": "131xxxx0000", // 选填，唯一
  "nickName": "张三",           // 选填，为空时服务端默认取 userName
  "deptId": 103,                // 选填，归属部门
  "email": "a@b.com",           // 选填，唯一
  "sex": "0",                   // 选填 0男1女2未知
  "status": "0",                // 选填 0正常1停用，默认正常
  "remark": "备注",             // 选填
  "roleKeys": ["common"]        // 选填，角色编码（sys_role.role_key），可多个
}
```
响应：`SaResult.ok()` / `SaResult.error(msg)`。

### 2.2 `updateUser`（需求2）
请求 body 字段（**只允许改本人资料**，`userId`/`tenantId` 服务端以会话为准，忽略 body 传入）：
```jsonc
{
  "nickName": "张三",           // 选填
  "phonenumber": "131xxxx0000", // 选填，唯一
  "email": "a@b.com",           // 选填，唯一
  "sex": "0"                    // 选填
}
```
响应：`SaResult.ok()` / `SaResult.error(msg)`。

> ✅ **按需更新（非全量覆盖）**：body 中哪个字段传了就改哪个，**未传（null/空）的字段保持原值不动**，
> 不会把用户没填的字段清空。因此前端只提交"改动过的字段"即可（实现见 §4.3 条件 set）。

## 3. 需求1：新增用户（`addUser`）

### 3.1 改动文件
- `cloud-auth-platform-auth/.../controller/SsoServerController.java`（新增 handler）

### 3.2 新增 handler（放入 `configAuth(SaSsoServerTemplate)` 方法体内，与 `updatePassword` 相邻）

```java
// 【登录态】新增用户：操作人（当前登录用户）在其所属租户下创建新用户，支持用户名/密码/手机/角色编码等
ssoServerTemplate.messageHolder.addHandle("addUser", (tpl, message) -> {
    String client = message.getString("client");
    String loginId = message.getString("loginId");
    // 解析操作人身份：新增用户归属到操作人所在租户，防止跨租户越权创建
    String loginToken = getLoginTokenByClient(client, loginId);
    LoginUser operator = LoginHelper.getLoginUser(loginToken);
    if (operator == null) {
        return SaResult.error("操作人登录态已失效，请重新登录");
    }
    RemoteUserBo bo = JsonUtils.parseObject(message.getString("body"), RemoteUserBo.class);
    if (bo == null || !StringUtils.hasText(bo.getUserName())) {
        return SaResult.error("用户账号不能为空");
    }
    // 归属维度以操作人会话为准，忽略 body 传入的 tenantId/clientId
    bo.setTenantId(operator.getTenantId());
    bo.setClientId(client);
    // 密码：为空交由 registerUserInfo 走默认密码；非空则在此加密（registerUserInfo 不对入参密码加密）
    if (StringUtils.hasText(bo.getPassword())) {
        bo.setPassword(cn.hutool.crypto.digest.BCrypt.hashpw(bo.getPassword()));
    } else {
        bo.setPassword(null);
    }
    // 昵称为空默认取账号，保持与注册一致
    if (!StringUtils.hasText(bo.getNickName())) {
        bo.setNickName(bo.getUserName());
    }
    try {
        Boolean ok = remoteUserService.registerUserInfo(bo);
        return Boolean.TRUE.equals(ok) ? SaResult.ok() : SaResult.error("新增用户失败");
    } catch (ServiceException | UserException e) {
        return SaResult.error(e.getMessage());
    }
});
```

### 3.3 需要补充的 import（`SsoServerController.java` 顶部，若尚未存在）
```java
import io.gitee.chenshaogui.cloudauth.common.core.exception.ServiceException;
import io.gitee.chenshaogui.cloudauth.common.core.exception.user.UserException;
// BCrypt 用全限定名 cn.hutool.crypto.digest.BCrypt，或 import cn.hutool.crypto.digest.BCrypt;
```
> `RemoteUserBo`、`LoginUser`、`LoginHelper`、`JsonUtils`、`StringUtils`、`SaResult` 该文件已 import。

### 3.4 说明
- 复用 `registerUserInfo` 天然获得：用户名唯一校验、手机号唯一校验、默认密码兜底、
  按 `roleKeys` 自动绑定角色（`autoBindRolesByRoleKeys`，超级管理员角色禁止经此通道绑定，防提权）。
- `roleKeys` 为**角色编码**（`sys_role.role_key`），由**接入 SDK 的业务系统**自行传入并透传到本 handler；
  当前 SDK 工程只提供"把 roleKeys 带给认证中心"的能力，**不决定绑定哪些角色**（与注册链路
  `sa-token.register-role-keys` 自动兜底不同，`addUser` 不做任何默认注入，接入系统传什么就绑什么）。
  若传的是短标识，服务端会按 `{clientId}-{短标识}` 兼容补全。
- 若业务要求“新增用户必须校验操作人是否有 `system:user:add` 权限”，可在 handler 内加
  `LoginHelper.getLoginUser(loginToken).getMenuPermission().contains("system:user:add")` 判断，
  或交由 SDK 侧端点的权限注解控制（见 §6 安全说明）。

### 3.5 追加需求（已落地）：用户已存在且有 `roleKeys` 时补绑角色

> 需求：`addUser` 时若账号在操作人租户下已存在，且请求带 `roleKeys`，不再报"账号已存在"，
> 而是给这个既有用户**追加绑定**命中的角色，返回既有 `userId`；未带 `roleKeys` 时行为不变。
>
> 决策：**不新开入口**，直接在现有 `addUser` 总线 handler 内分流。SDK 端点 `/authCenter/addUser`
> 与 `CloudAddUserBo` 契约不变（本来就透传 `roleKeys`、返回 `Long userId`），接入系统无需改代码。

服务端改动文件（5 个）：

| 文件 | 改动 |
|---|---|
| `api-system/.../RemoteUserService.java` | 新增 `Long bindRolesIfUserExists(RemoteUserBo)`：用户存在返回既有 userId，不存在返回 null |
| `system/.../dubbo/RemoteUserServiceImpl.java` | 实现该方法，委托 `userService.bindRolesIfUserExists(...)` |
| `system/.../service/ISysUserService.java` | 新增 `bindRolesIfUserExists(userName, roleKeys, tenantId, clientId)` 声明 |
| `system/.../service/impl/SysUserServiceImpl.java` | 按 userName 在租户内查用户并补绑角色；把注册用的 `autoBindRolesByRoleKeys` 与补绑共用为 `bindRoleKeys(...)`；新增绑定后发布 `PermissionChangeEvent(UPDATE)` |
| `auth/.../controller/SsoServerController.java` | `addUser` handler 在 `roleKeys` 非空时先调用补绑方法，命中即 `SaResult.ok().setData(existingUserId)`；未命中才继续走 `registerUserInfo` |

`bindRoleKeys(userId, roleKeys, clientId, onlyWhenNoRoles)` 的两种语义：

| 语义 | onlyWhenNoRoles | 行为 |
|---|---|---|
| 注册（新用户） | `true` | 用户已有任何角色绑定则整体跳过（**保持原行为**） |
| addUser 已存在用户 | `false` | 保留已有绑定，只插入缺失的 roleId（幂等、不覆盖、不删除） |

两条通道共用规则不变：role_key 双格式兼容（短标识自动补 `{clientId}-`）、只命中启用状态角色、
超级管理员角色禁止绑定（防提权）、未命中静默跳过仅记 warn 日志；均在事务内执行，失败整体回滚。

**边界与兼容**：

| 场景 | 结果 |
|---|---|
| 账号不存在（有无 `roleKeys` 均可） | 正常走 `registerUserInfo` 新建用户，返回新 `userId` |
| 账号已存在 + 无 `roleKeys` | 与改造前一致：`registerUserInfo` 抛"账号已存在" |
| 账号已存在 + `roleKeys` | 不新建、不改密码/资料，只追加角色，返回既有 `userId`；重复调用不产生重复绑定 |
| 账号已存在 + `roleKeys` 全部无效 / 角色停用 | 返回成功 + 既有 `userId`，服务端仅记 warn 日志 |
| 越权 | 用户按操作人会话的 `tenantId` 查找；短标识只会命中当前 `clientId` 的角色；租户与客户端均忽略 body 传入 |

无表结构变更（复用 `sys_user` / `sys_role` / `sys_user_role`）。部署顺序与注册自动绑定角色一致：
先发布 `api-system`（Dubbo 两端共用新接口），再发布 `system` 与 `auth`，否则消费方调用新方法会报方法不存在。

### 3.6 追加需求（已落地）：启用/停用其他用户（`updateUserStatus`）+ 审计日志

> 需求：管理员可启用/停用其他用户；权限由接入系统菜单自行控制（服务端不加权限字符校验），
> 只做“只能操作同租户用户”的硬隔离与“禁止禁用超级管理员”护栏，并写审计日志以便追溯。

服务端改动文件（5 个）：

| 文件 | 改动 |
|---|---|
| `api-system/.../RemoteUserService.java` | 新增 `Boolean updateUserStatus(RemoteUserBo)` 与 `Long selectUserIdByUserName(userName, tenantId)` |
| `system/.../dubbo/RemoteUserServiceImpl.java` | 实现上述两方法：updateUserStatus 在 `TenantHelper.dynamic(tenantId)` 内委托系统用户服务；selectUserIdByUserName 在租户内按账号精确匹配未删除用户、跨租户/不存在返回 null |
| `system/.../service/ISysUserService.java` | 新增 `updateUserStatus(userId, status, tenantId)` 重载 |
| `system/.../service/impl/SysUserServiceImpl.java` | 实现重载：UPDATE 追加 `eq(tenant_id, tenantId)`，跨租户 userId 因不匹配而更新 0 行（安全）；禁用时仍踢下线 |
| `auth/.../controller/SsoServerController.java` | 新增 `updateUserStatus` 总线 handler + `writeUserStatusAudit` 审计日志；以操作人会话租户为准覆盖 body 的 tenantId/clientId，**支持 userId 或 userName 定位目标**（仅传 userName 时先在操作人租户内解析为 userId），禁止禁用超管 |

SDK 侧改动（2 个文件）：新增 `CloudUpdateUserStatusBo`（`userId` / `userName` 二选一 + `status`）、
`CloudPlatformHelper` 提供**两个入口** `updateUserStatusByUserId(Long,String)` / `updateUserStatusByUsername(String,String)`
（均返回 {@code boolean}：成功 {@code true}，业务失败 {@code false}），
以及 `enable/disable` 便捷方法（按 userId / 按 userName 各一对，同样返回 {@code boolean}）。

> **注意（权限下放）**：SDK 不再在 `CloudAuthCenterController` 暴露 `updateUserStatus` HTTP 端点；
> 权限由接入系统在其自建接口中承担，接入系统应在自身接口加权限校验后调用 `CloudPlatformHelper` 的上述方法（均走同一总线 handler，契约不变）。

**安全保证（防 SDK 误禁/跨租户禁用）**：

| 维度 | 实现 |
|---|---|
| 租户隔离 | handler 解析操作人登录态取 `tenantId`，覆盖 body 传入值；UPDATE 语句强制 `tenant_id = 操作人租户`，其他租户用户匹配 0 行、不会被改 |
| 操作人身份 | `loginId → 服务端 getLoginTokenByClient` 重新校验，与 `addUser` 同一信任模型，SDK 无法冒充他人 |
| 超管护栏 | `status=1` 且目标为 `SUPER_ADMIN_ID` 直接拒绝（保证可被追溯） |
| 权限控制 | 由客户端菜单权限负责，服务端不校验权限字符 |
| 审计追溯 | 每次调用（成功/拒绝/非法状态）均写 `sys_oper_log`（title=启用/停用用户，含 targetUserId、操作人、客户端、租户） |

**边界**：`status` 仅接受 `0/1`，其它值报“非法的账号状态”；目标不存在、跨租户或已删除返回“用户不存在或无权限”。

**定位方式**：入参 `userId` 与 `userName` 二选一，优先 `userId`；仅传 `userName` 时由服务端在**操作人会话所属租户**内解析为 userId（跨租户 / 不存在 / 已删除解析不到 → 报“用户不存在或无权限”），避免越权定位其他租户账号。

### 3.7 追加需求：`deleteUser`（删除用户：仅解绑角色 / 删用户）

> 需求：管理员可解除某用户与某角色的绑定；若该用户**仅绑定这一个角色**，解除后无角色，则**删除用户**；否则**仅解除角色绑定**。权限由接入系统菜单自行控制（服务端不加权限字符校验），同样做租户硬隔离与超管护栏，并写审计日志。

服务端改动文件（在 3.6 基础上再改 4 个）：

| 文件 | 改动 |
|---|---|
| `api-system/.../RemoteUserService.java` | 新增 `Boolean deleteUser(RemoteUserBo)`（throws ServiceException） |
| `system/.../dubbo/RemoteUserServiceImpl.java` | 实现 `deleteUser`：在 `TenantHelper.dynamic(tenantId)` 内查用户当前角色；不属于该角色抛 `ServiceException("用户不属于该角色，无需解除")`；仅绑定该唯一角色 → 委托 `deleteUserById` 删除用户；多个角色 → 委托 `unbindUserRole` 仅解绑 |
| `system/.../service/ISysUserService.java` | 新增 `int unbindUserRole(Long, Long)`（`deleteUserById` 服务端已有，直接复用） |
| `system/.../service/impl/SysUserServiceImpl.java` | 新增 `unbindUserRole`：仅删 `sys_user_role` 关联（保留用户）并踢下线 + 权限同步（UPDATE）；删除用户复用已有 `deleteUserById`（含角色/岗位/客户端关联清理、踢下线、权限同步） |
| `auth/.../controller/SsoServerController.java` | 新增 `deleteUser` 总线 handler + `writeUserDeleteAudit` 审计日志；以操作人会话租户为准覆盖 tenantId/clientId，支持 userId/userName 定位，禁止操作超管 |

SDK 侧改动（2 个文件）：新增 `CloudDeleteUserBo`（`userId` / `userName` 二选一 + `roleId`）、
`CloudPlatformHelper` 提供**两个入口** `deleteUserByUserId(Long, Long)` / `deleteUserByUsername(String, Long)`
（均返回 {@code boolean}：成功 {@code true}，业务失败 {@code false}）。

> **注意（权限下放）**：与 `updateUserStatus` 一致，SDK 不暴露 HTTP 端点；接入系统自建接口加权限校验后调用上述方法。

**安全保证（与 3.6 同一套信任模型）**：租户隔离、操作人身份重校验、审计追溯同 3.6；新增——超管护栏：目标为 `SUPER_ADMIN_ID` 直接拒绝（不允许删除/解绑超级管理员）。

**边界（deleteUser）**：

- `userId`/`userName` 与 `roleId` 均不能为空，否则报“用户ID或账号、角色ID不能为空”。
- 目标不存在、跨租户或已删除 → “用户不存在或无权限”（userName 解析不到）。
- 用户**不属于**传入的 `roleId` → “用户不属于该角色，无需解除”（返回 {@code false}）。
- 用户**仅绑定该唯一角色** → 解除后无角色，**删除用户**（含角色/岗位/客户端/扩展关联清理、踢下线、权限同步）。
- 用户**绑定多个角色** → **仅解除该角色绑定**，保留用户。
- 目标为超级管理员（userId=1）→ 拒绝（无论解绑还是删除），与“禁止禁用超级管理员”护栏一致。

## 4. 需求2：修改当前登录人信息（`updateUser`）

### 4.1 改动文件
- `cloud-auth-platform-api/.../system/api/RemoteUserService.java`（接口新增方法）
- `cloud-auth-platform-modules/.../system/dubbo/RemoteUserServiceImpl.java`（实现）
- `cloud-auth-platform-auth/.../controller/SsoServerController.java`（新增 handler）

### 4.2 `RemoteUserService` 接口新增
```java
/**
 * 修改用户个人资料（昵称/手机号/邮箱/性别）——供认证中心 SDK 总线“修改当前登录人信息”调用。
 * <p>仅更新资料字段，不涉及角色/状态/账号；手机号、邮箱做唯一性校验（按 userId 排除自身）。</p>
 *
 * @param remoteUserBo 需包含 userId、tenantId 及待更新资料字段
 * @return 是否更新成功
 */
boolean updateUserProfile(RemoteUserBo remoteUserBo);
```

### 4.3 `RemoteUserServiceImpl` 实现（**按需更新：只改传入的字段，绝不全量覆盖**）
> **不复用** `ISysUserService.updateUserProfile`——它对 `phonenumber/email/sex` 是无条件 `set`，
> 会把本次未传的字段清空。这里直接用 `LambdaUpdateWrapper` 做**条件 set**：字段 `isNotBlank` 才更新，
> 未传的保持原值。
```java
@Override
public boolean updateUserProfile(RemoteUserBo remoteUserBo) {
    if (remoteUserBo == null || remoteUserBo.getUserId() == null) {
        throw new ServiceException("用户ID不能为空");
    }
    return TenantHelper.dynamic(remoteUserBo.getTenantId(), () -> {
        // 唯一性校验仅在“该字段本次有传值”时才做（checkXxxUnique 内部按 userId 排除自身）
        if (StringUtils.isNotBlank(remoteUserBo.getPhonenumber())) {
            SysUserBo phoneQ = new SysUserBo();
            phoneQ.setUserId(remoteUserBo.getUserId());
            phoneQ.setPhonenumber(remoteUserBo.getPhonenumber());
            if (!userService.checkPhoneUnique(phoneQ)) {
                throw new ServiceException("手机号码已存在");
            }
        }
        if (StringUtils.isNotBlank(remoteUserBo.getEmail())) {
            SysUserBo emailQ = new SysUserBo();
            emailQ.setUserId(remoteUserBo.getUserId());
            emailQ.setEmail(remoteUserBo.getEmail());
            if (!userService.checkEmailUnique(emailQ)) {
                throw new ServiceException("邮箱账号已存在");
            }
        }
        // 条件 set：传了才改，没传不动，避免清空未提交字段
        int rows = DataPermissionHelper.ignore(() -> userMapper.update(null,
            new LambdaUpdateWrapper<SysUser>()
                .set(StringUtils.isNotBlank(remoteUserBo.getNickName()), SysUser::getNickName, remoteUserBo.getNickName())
                .set(StringUtils.isNotBlank(remoteUserBo.getPhonenumber()), SysUser::getPhonenumber, remoteUserBo.getPhonenumber())
                .set(StringUtils.isNotBlank(remoteUserBo.getEmail()), SysUser::getEmail, remoteUserBo.getEmail())
                .set(StringUtils.isNotBlank(remoteUserBo.getSex()), SysUser::getSex, remoteUserBo.getSex())
                .eq(SysUser::getUserId, remoteUserBo.getUserId())));
        // 四个字段全未传时无 set 列，rows 可能为 0，按“无改动”视作成功
        return true;
    });
}
```
> `SysUserBo`、`LambdaUpdateWrapper`、`SysUser`、`DataPermissionHelper`、`TenantHelper`、`StringUtils`、`ServiceException`
> 及 `userMapper`（该类的 `SysUserMapper` 字段）在 `RemoteUserServiceImpl.java` 均已存在。

### 4.4 `SsoServerController` 新增 handler（放 `configAuth` 内）
```java
// 【登录态】修改当前登录人信息：userId/tenant 一律取会话，禁止改他人；仅放开资料字段
ssoServerTemplate.messageHolder.addHandle("updateUser", (tpl, message) -> {
    String client = message.getString("client");
    String loginId = message.getString("loginId");
    String loginToken = getLoginTokenByClient(client, loginId);
    LoginUser operator = LoginHelper.getLoginUser(loginToken);
    if (operator == null) {
        return SaResult.error("登录态已失效，请重新登录");
    }
    RemoteUserBo bo = JsonUtils.parseObject(message.getString("body"), RemoteUserBo.class);
    if (bo == null) {
        return SaResult.error("参数不能为空");
    }
    // 只允许改本人：身份维度以会话为准，忽略 body 传入
    bo.setUserId(operator.getUserId());
```

## 5. 需求3：注册密码可不填 → 默认密码

### 5.1 改动文件
- `cloud-auth-platform-auth/.../form/RegisterBody.java`
- `cloud-auth-platform-auth/.../service/SysLoginService.java`
- （`RemoteUserServiceImpl.registerUserInfo` **无需改**，默认密码逻辑已存在）

### 5.2 `RegisterBody.java`：放开密码必填
把 `password` 字段的校验注解去掉（或改为“非空时才校验长度”）。当前：
```java
@NotBlank(message = "{user.password.not.blank}")
@Length(min = 5, max = 30, message = "{user.password.length.valid}")
private String password;
```
改为：
```java
// 密码选填：为空时由服务端使用默认密码（sys.user.initPassword）
@Length(min = 5, max = 30, message = "{user.password.length.valid}")
private String password;
```
> 说明：Hibernate `@Length` 对 `null` 不校验、但对空串 `""` 会因 `min=5` 失败。
> 因此需配合 §5.3：在 `SysLoginService.register` 里把空串归一为 `null` 再走后续逻辑；
> 若想彻底避免空串触发 `@Length`，可连 `@Length` 一并移除，把长度校验放到 service 里“密码非空时”再判。

### 5.3 `SysLoginService.register(...)`：密码非空才加密，空则交给默认密码
把第 222 行：
```java
remoteUserBo.setPassword(BCrypt.hashpw(password));
```
改为：
```java
// 密码选填：非空才校验长度并加密；为空则保持 null，由 registerUserInfo 走默认密码 sys.user.initPassword
if (StringUtils.isNotBlank(password)) {
    if (password.length() < 5 || password.length() > 30) {
        throw new UserException("user.password.length.valid"); // 或按项目既有 i18n key 处理
    }
    remoteUserBo.setPassword(BCrypt.hashpw(password));
} else {
    remoteUserBo.setPassword(null);
}
```
> `StringUtils`、`BCrypt`、`UserException` 该文件已 import。
> 若项目里 `user.password.length.valid` 不是 `UserException` 的合法 i18n key，
> 可改用 `throw new ServiceException("密码长度需在5-30个字符之间")`。

### 5.4 默认密码来源
`RemoteUserServiceImpl.registerUserInfo` 读取参数配置 `sys.user.initPassword`（`ISysConfigService.selectConfigByKey`）。
**上线前确认该参数在目标租户下已配置**（通常默认 `abc@1234`），否则空密码注册会 NPE。
建议加一层兜底：
```java
String initPassword = configService.selectConfigByKey("sys.user.initPassword");
if (StringUtils.isBlank(initPassword)) {
    initPassword = "abc@1234"; // 兜底默认密码，避免配置缺失导致注册失败
}
```

## 6. SDK 侧配套改动（本仓库 `cloud-auth-client-oauth`，已实现于 v1.5.4）

服务端补齐 `addUser` / `updateUser` 两个 handler 后，SDK 侧按现有 `updatePassword` 同款写法补三处即可：

> **返回类型均为具体类型，不再用 `Object`**：`addUser` 返回 `Long`（新用户 id）、`updateCurrentUser`
> 与 `updatePassword` 返回 `boolean`（成功即 true；失败抛异常由全局处理器转 HTTP）。

1. **BO**（`bean` 包）
   - `CloudAddUserBo`：`userName / password / phonenumber / nickName / deptId / email / sex / status / remark / roleKeys(List<String>)`
   - `CloudUpdateUserBo`：`nickName / phonenumber / email / sex`
2. **`CloudPlatformHelper`**（复用 `callApi + wrapBodyLogin`，自动注入 `loginId`）
   ```java
   // 返回 Long：新用户 userId
   public static Long addUser(CloudAddUserBo body) {
       requireLogin();
       return callApi("addUser", wrapBodyLogin(body), Long.class);
   }
   // 返回 boolean：成功即 true；失败抛异常，由全局异常处理器转 HTTP
   public static boolean updateCurrentUser(CloudUpdateUserBo body) {
       requireLogin();
       callApi("updateUser", wrapBodyLogin(body));
       return true;
   }
   ```
3. **`CloudAuthCenterController`**（`/authCenter`，需登录）
   ```java
   @PostMapping("/addUser")
   public SaResult addUser(@RequestBody CloudAddUserBo body) {
       Long userId = CloudPlatformHelper.addUser(body);
       return SaResult.data(userId);
   }

   @PostMapping("/updateUser")
   public SaResult updateUser(@RequestBody CloudUpdateUserBo body) {
       CloudPlatformHelper.updateCurrentUser(body);
       return SaResult.ok();
   }
   ```
> **角色编码（roleKeys）为纯透传字段**：`CloudAddUserBo.roleKeys` 由接入 SDK 的业务系统自行填充，
> SDK 只做 JSON 序列化随 `addUser` 消息发出，**不注入默认值、不做角色决策**——当前项目只提供能力，
> 具体怎么用由接入系统决定。
>
> 注册密码可选：SDK 侧 `CloudRegisterBo.password` 已是普通字段（无强校验），
> 前端不传密码即走服务端默认密码，SDK 无需改动。

## 8. 安全与注意事项

1. **越权防护**：`addUser` / `updateUser` 的 `tenantId`、`userId` 一律以**操作人会话**为准，
   绝不信任 body 传入（handler 已显式覆盖）。
2. **提权防护**：`updateUser` 明确清空 `userName/roleKeys/status`，用户自助改资料不能改角色/状态；
   `addUser` 复用 `autoBindRolesByRoleKeys`，其内部禁止绑定超级管理员角色。
3. **权限控制**：`addUser` 属管理动作，建议在 SDK 端点或 handler 增加 `system:user:add` 权限校验；
   `updateUser` 为本人资料，登录即可。
4. **默认密码配置**：确认 `sys.user.initPassword` 在各租户已配置（§5.4 已给兜底建议）。
5. **密码加密位置**：`registerUserInfo` **不对入参密码加密**，所有调用方（注册、addUser）
   必须在传入前自行 `BCrypt.hashpw`；为空时由 `registerUserInfo` 兜底默认密码。
6. **资料按需更新**：`updateUser` 采用条件 set，**只改传入字段**，未传字段保持原值，
   不会清空用户未提交的资料（实现见 §4.3）。
7. **权限同步**：`updateUser` 改的是资料字段，不触发角色变更，无需 `publishUserChange`；
   若后续放开角色修改，需走 `updateUser`（SysUserServiceImpl）并触发权限变更通知。
