# 认证中心服务端改造说明 —— 只退同一浏览器（browserId 收敛）

> 配套 SDK：`cloud-auth-client-oauth`（`ssoLogout` 已改为"优先按浏览器登出、失败自动回退原生广播"）。
> 本文只描述**服务端工程 `cloud-auth-platform`** 需要落地的改动。
> 目标：在子系统内点退出时，只登出**同一浏览器**里该账号的所有子系统会话，不影响该账号在其它浏览器/设备的登录。

---

## 0. 这次为什么这样改（重要，先读）

上一版改造失败复盘：当时把 SDK 的 `ssoLogout()` 里 sa-token 原生的单点登出广播**整个删掉**，换成一个授权中心**尚未实现**的 `remoteLogout` 总线调用，结果两头都不通 —— 子系统本地退了、授权中心与其它子系统都没退。

本版修正两点：

1. **SDK 侧加了安全回退**：`ssoLogout()` 先尝试 `remoteLogout`（按浏览器登出）；只要授权中心**没有该 handler / 返回非 200 / 调用异常**，就**自动回退到原生 `ssoLogout()` 广播**。因此：
   - 服务端**先不上**这套改动 → SDK 走原生广播，退出照常传播（行为与现在一致，不会断）；
   - 服务端**上了**这套改动 → SDK 走按浏览器登出，实现"只退同一浏览器"。
   - **部署顺序不再敏感**，SDK 与服务端谁先上都安全。
2. **修正 browserId 的来源（关键）**：实测发现授权中心 SPA 与子系统的 **cookie** 都是 `22442709-...`（一致），但授权中心前端 `request.ts` 的 `getOrCreateBrowserId()` 只读 **localStorage**、自己生成 UUID 放进 `X-Browser-Id` 头；而服务端 `BrowserIdFilter` 是 **header 优先**。结果：授权中心 token extra 里的 browserId 是 localStorage 那个值，**不等于** cookie；EMS 退出走整页跳转（无 header）用 cookie → `logoutByBrowser` 按 `22442709` 过滤时**跳过了授权中心 token**，所以授权中心一直在线。
   修法：**两端 Filter 一律 cookie 优先 + 回写 cookie**，让 cookie 成为唯一真源（SDK 两个 `BrowserIdFilter` 已改；服务端 Filter 见下方“改动 0”）。**不再涉及域名/父域推导**（那是上一版的错误方向，已废弃）。

### 传播链路（本版）

子系统感知"自己被登出"靠的是**每请求节流的 `checkPermission` 轮询**（默认约 20s，见 `sa-token.cache.ttl-seconds`）：轮询发现授权中心侧本浏览器已无有效 token → 返回 401 → 子系统本地登出。因此服务端要保证两件事：

- **登出时只杀同浏览器的授权中心 token**（`remoteLogout` → `logoutByBrowser`）；
- **`checkPermission` / `isLogin` 感知时按 browserId 过滤**（否则同账号在别的浏览器还在线，会被误判为"仍登录"，本浏览器就不退了）。

### 改动 0（前置，关键）：auth 端 BrowserIdFilter 改为 cookie 优先

文件：`cloud-auth-platform-auth/src/main/java/io/gitee/chenshaogui/cloudauth/auth/filter/BrowserIdFilter.java`

把整个 `doFilter` 方法体替换为下面这版。要点：**cookie 优先**（而不是 header 优先），且只要 cookie 缺失或与最终值不一致就**回写 cookie**，让同一浏览器的 browserId 最终收敛到 cookie 这一个值。

```java
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest http = (HttpServletRequest) req;
        HttpServletResponse out = (HttpServletResponse) res;

        String browserId = null;
        String fromCookie = null;

        // 1. 优先 cookie：cookie 是同一浏览器在授权中心与各子系统之间唯一共享的介质，作为唯一真源。
        //    不能 header 优先：前端拦截器可能从 localStorage 生成一个与 cookie 不同的 X-Browser-Id，
        //    若 header 优先，会把那个值写进 token extra，导致与其它系统的 browserId 不一致、登出杀不掉。
        Cookie[] cookies = http.getCookies();
        if (cookies != null) {
            for (Cookie c : cookies) {
                if (COOKIE_NAME.equals(c.getName())) {
                    fromCookie = c.getValue();
                    break;
                }
            }
        }
        browserId = fromCookie;

        // 2. 没有 cookie 再用 header（兼容前端显式传入 / 服务端转发）
        if (browserId == null || browserId.isEmpty()) {
            browserId = http.getHeader(HEADER_NAME);
        }

        // 3. 仍没有则生成新 id（首次访问）
        if (browserId == null || browserId.isEmpty()) {
            browserId = IdUtil.simpleUUID();
        }

        // 4. cookie 缺失，或 cookie 与最终解析值不一致时回写，让所有系统最终收敛到同一个 cookie 值。
        //    例如首次由 header 种下时，把该值固化到 cookie，后续其它系统一律以它为准。
        if (fromCookie == null || !fromCookie.equals(browserId)) {
            Cookie cookie = new Cookie(COOKIE_NAME, browserId);
            cookie.setPath("/");
            cookie.setMaxAge(60 * 60 * 24 * 365); // 1 年
            cookie.setHttpOnly(false);
            out.addCookie(cookie);
        }

        BrowserIdContext.set(browserId);
        try {
            chain.doFilter(req, res);
        } finally {
            BrowserIdContext.clear();
        }
    }
```

> 与此对应，SDK 的 `BrowserIdFilter` / `BrowserIdFilterJakarta` 已改为同样的“cookie 优先 + 回写”逻辑（已在 SDK 侧提交）。两端都改后，授权中心 SPA 与各子系统写进 token 的 browserId 才会真正一致。
> **注意**：改完后，存量 token（用旧 header 值写的）不匹配，需重新登录一次才会对上。

### 改动 1：SysLoginService 抽出 logoutByBrowser

文件：`cloud-auth-platform-auth/src/main/java/io/gitee/chenshaogui/cloudauth/auth/service/SysLoginService.java`

现有 `logout()`（认证中心自身退出，约 123–176 行）已经是"按 browserId 过滤踢 token"的逻辑。把它内部那段"遍历 token、按 browserId 过滤后 `logoutByTokenValue`"抽成独立方法，供 `logout()` 与新的 `remoteLogout` 复用。

新增方法：

```java
    /**
     * 按 browserId 维度登出：杀掉该 loginId 下、属于"同一浏览器"（browserId 相同）的所有 token，
     * 不影响该账号在其它浏览器/设备的会话。供认证中心自身退出（{@link #logout()}）与
     * 子系统发起的远程登出（总线 handler {@code remoteLogout}）复用。
     *
     * @param loginId   账号 id（sa-token loginId，形如 userType:userId）
     * @param browserId 浏览器维度 id；<b>为空时不做任何登出</b>（避免退化成 loginId 全端登出、误踢其它浏览器）。
     *                  子系统发起登出但无法提供 browserId 时，其本地登出即可，无需广播。
     */
    public void logoutByBrowser(Object loginId, String browserId) {
        if (loginId == null) {
            return;
        }
        // 关键：没有明确 browserId 绝不广播，防止退化成 loginId 全端登出
        if (browserId == null || browserId.isEmpty() || "null".equals(browserId)) {
            return;
        }
        List<String> tokens;
        try {
            tokens = StpUtil.getTokenValueListByLoginId(loginId);
        } catch (Exception e) {
            tokens = Collections.emptyList();
        }
        for (String token : tokens) {
            try {
                Object tBid = StpUtil.getExtra(token, LoginHelper.BROWSER_ID_KEY);
                String tBidStr = tBid == null ? null : String.valueOf(tBid);
                // 只踢完全同 browserId 的 token；老 token(extra 无 browserId) 不匹配，跳过
                if (browserId.equals(tBidStr)) {
                    StpUtil.logoutByTokenValue(token);
                }
            } catch (Exception ignored) {
            }
        }
    }
```

然后把现有 `logout()` 里"解析 loginId + browserId 后遍历踢 token"的那段，改为解析出 `loginId`、`myBrowserId` 后调用 `logoutByBrowser(loginId, myBrowserId)`（行为等价，纯重构）。解析逻辑保持你现有实现即可：

```java
        Object loginId = StpUtil.getLoginIdDefaultNull();
        Object extraBid = StpUtil.getExtra(LoginHelper.BROWSER_ID_KEY);
        String myBrowserId = extraBid == null ? null : String.valueOf(extraBid);
        // 认证中心自身退出：历史 token 无 browserId 时，生成一个"只匹配它自己"的一次性 id，
        // 保证不会按 loginId 误广播到其它浏览器。
        if (myBrowserId == null || myBrowserId.isEmpty() || "null".equals(myBrowserId)) {
            myBrowserId = java.util.UUID.randomUUID().toString();
        }
        logoutByBrowser(loginId, myBrowserId);
```

> 现有 import 已含 `StpUtil`、`java.util.List`、`java.util.Collections`、`LoginHelper`，无需新增；`java.util.UUID` 用全限定名。

### 改动 2：SsoServerController 感知过滤 + 新增 remoteLogout

文件：`cloud-auth-platform-auth/src/main/java/io/gitee/chenshaogui/cloudauth/auth/controller/SsoServerController.java`

#### 2.1 getLoginTokenByClient 增加带 browserId 的过滤重载

把现有 `private String getLoginTokenByClient(String clientId, String loginId)`（约 912–952 行）改为"两参委托三参 + 三参带过滤"：

```java
    private String getLoginTokenByClient(String clientId, String loginId) {
        return getLoginTokenByClient(clientId, loginId, null);
    }

    /**
     * @param browserId 浏览器维度 id：<b>非空</b>时只认"同一浏览器"签发的 token（token extra 的 browserId 相等）；
     *                  <b>为空</b>时不过滤（向后兼容旧 SDK / 无 browserId 的调用）。
     */
    private String getLoginTokenByClient(String clientId, String loginId, String browserId) {
        if (!StringUtils.hasText(clientId) || !StringUtils.hasText(loginId)) {
            throw new NotPermissionException("client、loginId不能为空");
        }
        List<String> tokenIds;
        try {
            tokenIds = StpUtil.getTokenValueListByLoginId(loginId);
        } catch (Exception e) {
            throw NotLoginException.newInstance(StpUtil.stpLogic.loginType, "-1", "未能读取到有效token或者token已过期", null).setCode(11011);
        }
        List<SysUserOnline> userOnlineList = tokenIds.stream()
            .filter(token -> StpUtil.stpLogic.getTokenActiveTimeoutByToken(token) >= -1)
            // 仅当客户端上报了 browserId 时，才只认同一浏览器的 token
            .filter(token -> {
                if (!StringUtils.hasText(browserId)) {
                    return true;
                }
                Object tBid = StpUtil.getExtra(token, LoginHelper.BROWSER_ID_KEY);
                return browserId.equals(tBid == null ? null : String.valueOf(tBid));
            })
            .map(token -> {
                LoginUser loginUser = LoginHelper.getLoginUser(token);
                if (loginUser == null) {
                    return null;
                }
                String redisKey = CacheConstants.ONLINE_TOKEN_KEY + token;
                return TenantHelper.dynamic(loginUser.getTenantId(), () -> (SysUserOnline) RedisUtils.getCacheObject(redisKey));
            })
            .filter(Objects::nonNull)
            .filter(online -> clientId.equals(online.getClientKey()))
            .toList();
        if (!userOnlineList.isEmpty()) {
            return userOnlineList.get(userOnlineList.size() - 1).getTokenId();
        }
        throw NotLoginException.newInstance(StpUtil.stpLogic.loginType, "-1", "未能读取到有效token或者token已过期", null).setCode(11011);
    }
```

> 保留你原方法里已有的写法（`TenantHelper.dynamic` 的具体调用形式、注释等），本处只新增 `browserId` 参数与那段 `.filter(...)`。

#### 2.2 isLogin handler 传入 browserId，并把"未命中"归一为 false

`configSso` 里的 `isLogin` handler（约 285–290 行）改为：

```java
        ssoServerTemplate.messageHolder.addHandle("isLogin", (ssoTemplate, message) -> {
            String client = message.getString("client");
            String loginId = message.getString("loginId");
            String browserId = message.getString("browserId");
            try {
                String loginToken = getLoginTokenByClient(client, loginId, browserId);
                return SaResult.ok().setData(StringUtils.hasText(loginToken));
            } catch (NotLoginException e) {
                // 本浏览器无有效会话 → 归一为 false（不是异常冒泡成 500），SDK 据此本地登出
                return SaResult.ok().setData(false);
            }
        });
```

#### 2.3 checkPermission handler 传入 browserId

`checkPermission` handler 里"服务端登录态校验"那段（约 611–617 行）改为：

```java
            String client = message.getString("client");
            String browserId = message.getString("browserId");
            try {
                getLoginTokenByClient(client, loginId, browserId);
            } catch (Exception e) {
                log.info("[permission-sync] userId={} 本浏览器服务端登录态已失效({})，通知客户端登出", userId, e.getMessage());
                return SaResult.get(HttpServletResponse.SC_UNAUTHORIZED, "登录状态已失效，请重新登录", null);
            }
```

> 其余 `checkPermission` 逻辑（参数校验、变更时间戳返回）不变。命中不到 → 401 → SDK `doCheckPermissionChange` 收到 `NotLoginException` 执行 `logoutQuietly()` 本地登出。

#### 2.4 新增 remoteLogout handler（子系统发起的按浏览器登出）

在 `configSso` 内（与 `isLogin`、`checkPermission` 同级）新增：

```java
        // 子系统发起的"同浏览器登出"：SDK 的 ssoLogout() 走 pushS 总线调用本 handler。
        // 只登出该 loginId 下、与上报 browserId 相同的认证中心 token（同浏览器），不广播到其它浏览器。
        // 其它子系统无需服务端主动推送——它们在下一次 checkPermission/isLogin 轮询中感知 401 并本地登出。
        ssoServerTemplate.messageHolder.addHandle("remoteLogout", (ssoTemplate, message) -> {
            String loginId = message.getString("loginId");
            String browserId = message.getString("browserId");
            if (!StringUtils.hasText(loginId)) {
                return SaResult.error("loginId 不能为空");
            }
            // browserId 为空：不做任何广播（避免退化成 loginId 全端登出）；SDK 本地仍会登出
            sysLoginService.logoutByBrowser(loginId, browserId);
            return SaResult.ok();   // 必须返回 200，SDK 据此判定"按浏览器登出成功"，不再回退原生广播
        });
```

> `sysLoginService` 已在类中以 `@RequiredArgsConstructor` 注入（`private final SysLoginService sysLoginService;`）。`StringUtils` 为 `org.springframework.util.StringUtils`（文件已 import）。`remoteLogout` 走 `pushS` 通道，已具备 `client + sign` 校验，无需登录态。

## 2. 端到端时序（改造后）

**子系统内点退出（ems → 授权中心）：**
1. 前端调 ems 后端 `GET /sso/logout` → SDK `ssoLogout()`。
2. SDK `tryRemoteLogoutByBrowser`：走总线 `remoteLogout`（带 `loginId` + `browserId`）。
3. 授权中心 `logoutByBrowser(loginId, browserId)`：只杀**本浏览器**在授权中心为各子系统签发的 token；返回 `SaResult.ok()`。
4. SDK 收到 200 → 本地 `StpUtil.logout()`（ems 即时登出）→ 返回登出响应。
5. 同浏览器内其它子系统（如 car）下一次 `checkPermission` 轮询：`getLoginTokenByClient(car, loginId, browserId)` 命中不到（本浏览器 token 已杀）→ 401 → car 本地登出。**同浏览器一起退**。
6. 其它浏览器/设备：browserId 不同，token 未被杀、轮询仍命中 → 不受影响。

**授权中心内点退出：** `/auth/logout` → `SysLoginService.logout()` → `logoutByBrowser` 杀本浏览器所有子系统 token；各子系统同靠轮询感知。

**服务端未上改动时：** 第 3 步 `remoteLogout` 返回非 200（未注册 type）→ SDK 自动回退原生 `ssoLogout()` 广播（按 loginId，会退到其它浏览器，但保证"一定能退"）。

## 3. 自测清单（部署后）

1. **单浏览器多子系统**：同一浏览器登录 ems、car → 在 ems 点退出 → 等 ≤ 一个 `checkPermission` 周期并触发 car 一次接口 → car 应跳登录页；ems 立即退。
2. **多浏览器隔离（本版核心）**：浏览器 1、浏览器 2 同账号登录 ems → 在浏览器 1 退出 → 浏览器 2 的 ems/car **应保持登录**（不被误踢）。
3. **降级安全**：授权中心先不部署本次改动，仅升级子系统 SDK → 退出仍能传播（走原生广播回退），EMS 日志可见 `[ssoLogout] 授权中心未按浏览器登出(code=...)，回退原生登出`。
4. **假阳性回归**：退出后用旧 token 复测受保护接口须 401。

## 4. 约束与注意

- **依赖 browserId 跨系统一致**：当前同 IP 部署天然满足。若将来把各子系统拆到**不同子域名**（`a.x.com` / `b.x.com`），host-only cookie 不再共享，需另行做 browserId 统一（父域 cookie 或经 ticket 下发），否则"只退同一浏览器"会退化为"各系统各退各的"。
- **感知有延迟**：非服务端主动推送，其它子系统退出延迟 ≈ 一个 `checkPermission` 节流周期（默认 20s）。要更快可调小 `sa-token.cache.ttl-seconds`。
- **迁移成本**：本次改动上线前登录、上线后才退出的存量会话，其 token extra 里 browserId 若缺失，`logoutByBrowser` 不匹配、`getLoginTokenByClient` 不带 browserId 时退化旧逻辑，不会误伤；建议低峰发布。
- **is-concurrent / is-share**：保持现状，多浏览器各自独立 token 正是按 browserId 隔离的基础。
