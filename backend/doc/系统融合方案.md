# 系统融合方案 — security_ln_pro → security-cloud

> 文档版本：v1.0
> 编制时间：2026-09-28
> 适用项目：cloud-auth-platform（基于 RuoYi-Cloud-Plus 的统一权限管理平台）
> 融合对象：`script\系统融合\security_ln_pro.sql`（原"辽宁省交通安全监管平台"，约 10.5 MB，42 张表）
> 融合目标：将 ln_pro 的存量数据（含用户、角色、部门、菜单权限、字典、日志、文件、区域等）平滑迁移到当前 security-cloud 数据库，不丢数据、不破坏现有体系。

---

## 一、项目背景

公司基于 **RuoYi-Cloud-Plus**（参考 README.md）搭建了新的统一授权平台 `cloud-auth-platform`，目前数据库为 `security-cloud.sql`。同时，公司还有一套运行多年的"辽宁省交通安全监管平台"，其数据库为 `security_ln_pro.sql`，沉淀了大量用户、角色、菜单权限、字典、日志、附件等业务数据。

业务诉求：
1. **统一登录**：后续所有子系统统一走 cloud-auth-platform 的认证授权。
2. **数据合并**：ln_pro 中的存量数据（用户、机构、权限、字典、附件、日志等）需迁入到 cloud 库。
3. **业务延续**：ln_pro 侧的部分特有业务表（如里程权益、重要标签、标准规范等）需要在 cloud 库中保留或重建。

由于两库**底层架构、主键策略、字段命名、租户模型**差异巨大，不能简单做"整库覆盖"，必须分阶段、可回退地完成融合。

### 2.1 数据库基本信息

### 3.7 菜单/权限：sys_menu / sys_role_menu ⇄ sys_sec_operation + sys_sec_opaction + sys_sec_role_operation + sys_sec_role_opt_action_data

#### 3.7.1 数据模型差异

ln_pro 是 **「operation(模块) → opaction(URL/操作)」** 二级模型，配合 `sys_sec_role_operation` 决定**哪些模块对角色可见**、按 `osearch/osave/oupdate/oremove` 控制模块内动作权限，再叠加 `sys_sec_role_opt_action_data` 引入**数据范围**（来自 `sys_sec_data`）。

cloud 是 **「menu(目录/菜单/按钮) → perms(权限字符串)」** 模型，按 `sys_role_menu` 关联，权限字符串用于注解拦截，无内置数据范围（用 `data_scope` 表达）。

#### 3.7.2 转换策略

**第一阶段：转换 operation → sys_menu**
- `sys_sec_operation.ID` → `sys_menu.menu_id`（雪花 ID 映射）
- `sys_sec_operation.NAME` → `sys_menu.menu_name`
- `sys_sec_operation.URI` → `sys_menu.path`
- `sys_sec_operation.COMPONENT` → `sys_menu.component`
- `sys_sec_operation.TYPE`（2=菜单/1=操作/...）→ `sys_menu.menu_type`（M=目录，C=菜单，F=按钮）
- `sys_sec_operation.PARENTID` → `sys_menu.parent_id`
- `sys_sec_operation.ICON` → `sys_menu.icon`
- `sys_sec_operation.PERMS` → `sys_menu.perms`
- `sys_sec_operation.ORDERNUM` → `sys_menu.order_num`
- `sys_sec_operation.HIDDEN` → `sys_menu.visible`（0 显示，1 隐藏）
- `sys_sec_operation.IS_ROUTE`、`KEEP_ALIVE`、`REDIRECT`、`INTERNAL_OR_EXTERNAL`、`CLASSNAME`、`CONFIG`、`LOGSTRING`、`REMEMBERLOG` → **新增 sys_menu_ext 表** 存放

**第二阶段：opaction 转按钮/细粒度**  
- 每个 opaction 视为"按钮权限"，插入到 sys_menu（menu_type='F'）
- `opaction.id`（URL）作为 `perms` 或 `path`，`optDesc` 作为 `menu_name`

**第三阶段：角色权限关联**
- `sys_sec_role_operation` → `sys_role_menu`（按 ROLEID + OPERATIONID 映射）
- `sys_sec_role_opt_action_data` 中的 `ACTIONID`（来自 sys_sec_action）映射为按钮权限，并附带数据范围

## 四、融合策略与设计原则

### 4.1 总体策略

> **"新增字段 + ID 映射 + 一次性迁移脚本 + 分阶段切换"**

1. **不破坏现有 cloud 表的主键与租户模型**：所有迁移目标 ID 一律**重新生成雪花 ID**，维护一份 `*_id_map` 映射表供关联表使用。
2. **ln_pro 独有字段**采用两种方式落地：
   - 与目标表语义相关 → **ALTER TABLE 新增字段**
   - 量大或无关 → **新建扩展表**（如 `sys_user_ext`、`sys_dept_ext`、`sys_menu_ext`）
3. **租户归一**：ln_pro 中的所有数据默认归入 `tenant_id='000000'`（系统租户）；如果需要保留"重点车辆监管平台"作为独立租户，可新建 `tenant_id='ln_pro'` 的记录。
4. **密码重置**：ln_pro 中部分密码是明文或 MD5，**统一改为临时密码 `Ln@2024`**，并**强制用户首次登录修改密码**（通过新增 `pwd_reset_flag` 字段）。
5. **数据校验**：迁移脚本必须输出**迁移行数、失败明细、抽样校验报告**。
6. **可回退**：迁移前完成 ln_pro 全量 `mysqldump` 备份；cloud 库迁移前全量备份；提供一键回退 SQL。

### 4.2 字段命名规范统一

| 类别 | ln_pro 来源（全大写） | cloud 目标（全小写） |
| --- | --- | --- |
| 主键列 | `ID` | `*_id` |
| 创建人 | `CREATEUSERID`/`CREATEBYUSERID` | `create_by` |
| 创建时间 | `CREATETIME` | `create_time` |
| 更新人 | `UPDATEBYUSERID` | `update_by` |
| 更新时间 | `UPDATETIME` | `update_time` |
| 删除标志 | `DELETEFLAG` | `del_flag` |

### 4.3 ID 映射表设计

为方便关联数据转换，建立如下映射辅助表（迁移专用，迁移完成后可保留或清理）：

```sql
CREATE TABLE _migration_id_map (
    source_table  VARCHAR(64)  NOT NULL,   -- 来源表
    source_id     VARCHAR(64)  NOT NULL,   -- 来源主键（varchar）
    target_table  VARCHAR(64)  NOT NULL,   -- 目标表
    target_id     BIGINT       NOT NULL,   -- 目标主键（雪花 ID）
    PRIMARY KEY (source_table, source_id),
    KEY idx_target (target_table, target_id)
);
```

按表分别维护：`sys_sec_user`, `sys_sec_role`, `sys_sec_department`, `sys_sec_operation`, `sys_sec_tenant`, `sys_dict`, `sys_operate_log`, `sys_sec_user` → `sys_social` 等。

| 风险 | 等级 | 缓解措施 |

public class SysUserExtServiceImpl implements ISysUserExtService {
